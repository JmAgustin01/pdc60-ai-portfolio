Kualta Agency Support Chatbot

A rules-first RAG chatbot on Facebook Messenger for a digital marketing agency. It quotes the agency's prices and policies exactly, answers everything else only from the agency's own content, and hands the chat to a person when it isn't sure.

The problem

Kualta Agency, a digital marketing startup, wanted a support assistant that could answer customer questions about services, prices and policies, capture leads, and pass serious conversations to the team. The first version used Tidio on WordPress. It worked as a demo, but we couldn't control how it retrieved content, what similarity counted as a match, or what the prompt said.

We rebuilt it from scratch as our own backend, connected to Facebook Messenger, so every part of the answer pipeline is visible and adjustable. The client later closed, so the team set the demo's business values (prices and policies) ourselves and kept them in a single config file.

Why rules first?

Prices and policies must never be paraphrased by an LLM. If the agency says the 50% deposit is non-refundable, the bot has to say exactly that. So fixed intents answer those questions directly, and the LLM only handles open questions, only from retrieved content.

How it works

1
Message arrives from Messenger

Meta's webhook delivers it. The server checks the signature and drops duplicate retries, so a slow start never causes double replies.

↓
2
Safety screen

Blocks prohibited data (card numbers via a Luhn check, passwords, bank details) and redacts it from logs. Abusive messages get three strikes, then the chat pauses for 24 hours.

↓
3
Session flows

Lead capture with a privacy notice and consent, consultation booking, after-hours replies, and a “DELETE MY DATA” command.

↓
4
Rules first

Questions about services, prices, discounts, policies and guarantees match fixed intents and get word-for-word answers from business-rules.json. Rules handle English, Taglish and typos.

no rule matched ↓
5
Retrieve

The question is embedded (Gemini embeddings, 1536 dimensions) and searched in Supabase pgvector. Only chunks above the 0.60 similarity cutoff count.

nothing relevant → fallback + human handoff, no LLM call ↓
6
Grounded answer

Gemini Flash answers only from the retrieved chunks. If it replies NO_ANSWER, the bot hands off instead of guessing.

↓
7
Reply and log

Sent through the Messenger Send API. Every message is logged with its route, sources and similarity score.

Human handoff

When the bot hands off, the team replies from the Meta Business Suite inbox and the bot stays quiet for that customer for 12 hours. Customers can also type HUMAN at any time. Messenger stays in development mode for the team, and outside testers, including our instructor, use a public web chat page that runs the same pipeline.

Client business rules in code

All agency values live in config/business-rules.json. Changing a price is a config edit and a redeploy, with no code changes. If a value is left empty, the bot hands off for that topic instead of guessing.

Testing and evaluation

My job on the team was training and testing the AI. Two layers of tests keep the bot honest:

  • 83 automated unit tests (Node's built-in test runner) for the rules engine, validators, Messenger webhook, RAG pipeline, conversation flows, knowledge loading and the web chat. They run without any API keys.
  • A 29-question evaluation set (tests/test-set.json) run by npm run eval against the live bot. Each question has the routes it may take (rule, RAG or fallback) and a written pass rule. Results are saved as CSV.

The evaluation set covers Filipino and Taglish questions, typos, single-word fragments, out-of-scope requests and a prompt-injection attempt. Results from the first Messenger test led to two fixes and to recalibrating the similarity cutoff to 0.60 for the new embedding model.

What I learned

  • An LLM is one step, not the whole system. Most of the reliability comes from what happens before the model is called: screening, fixed rules, retrieval thresholds and handoff.
  • “I don't know” is a feature. Skipping the LLM when nothing relevant is retrieved is cheaper and safer than letting it improvise.
  • Test sets beat demos. Writing pass rules before running the bot made it obvious when a change broke something, especially for Taglish and typo-heavy questions.
  • Thresholds need calibration. When we switched embedding models, the old similarity cutoff stopped making sense, and we had to re-tune it with real questions.
